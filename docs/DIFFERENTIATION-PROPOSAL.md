# INNO Workspace 차별점 정리와 강화 제안 (2026-10-06)

## 목적과 기준
- 질문: 같은 구독으로 ChatGPT(Codex)나 Claude(Claude Code·Routine)에 직접 작업을 맡기는 것과 비교해, INNO Workspace를 쓸 이유가 분명한가.
- 기준: 지금 코드와 운영에서 확인된 기능만 근거로 쓴다. INNO 플랫폼들(NanoLab·Prism 등)과의 연동은 장점에서 제외한다(사용자 결정).
- 상대 서비스의 세부 기능은 수시로 바뀐다. 아래 비교는 "한 회사의 서비스 안에서는 구조적으로 하기 어려운 것"을 기준으로 적는다.

## 1. 근거 있는 차별점

| 차별점 | 무엇을 하나 | 근거(현재 코드·운영) | 한 회사 서비스로 어려운 이유 |
|---|---|---|---|
| 서로 다른 회사 모델의 교차 작업·검증 | 한 작업을 Codex와 Claude 하위 작업으로 나누고(2~4개), 수용 기준과 근거로 검토하며, 실패 기준만 다시 맡긴다. 제공자 인계도 같은 기록 위에서 이어진다 | H7 위임·검토(운영 반영), 제공자 인계, 검토 관측 | 각 서비스는 자기 회사 모델만 실행한다. 다른 회사 모델이 결과를 독립적으로 검증하는 구조를 만들 수 없다 |
| API 요금 없는 다중 에이전트 조율 | 위임·검토·재시도·예약 실행·인계를 이미 쓰는 정액 구독으로 한다 | 구독 인증만 허용(PRV-02), 유료 API·초과 사용 금지 | 여러 에이전트를 묶는 도구 대부분은 종량제 API 키를 요구한다 |
| 연구 기록의 소유와 이동성 | 작업·대화·결정·결과물·사용량·실행 근거가 사용자 계정의 저장소(D1)에 남고 내보내기·가져오기가 된다. 모델이나 회사를 바꿔도 맥락이 이어진다 | 작업 저장소, 내보내기·가져오기, 원문 보존 원칙 | 대화 기록은 각 회사 계정에 갇혀 있고 회사 사이로 옮겨 이어 쓸 수 없다 |
| 원본 파일을 클라우드에 보관하지 않음 | PC 원본은 이 PC에서 읽고, 실행 때 필요한 범위만 전달한다. 클라우드에는 원본 파일이 저장되지 않는다 | 원본 비보관, 원본 범위 지정(source views), 일시 자료 전달 | 일반 업로드는 파일을 서비스에 보관한다. 단, 전달한 내용은 모델 회사로 간다(완전한 비공개가 아니라 '파일 보관을 남기지 않음'의 차이) |
| 끊겨도 잃지 않는 긴 작업 | 실행 소유권·임대·결과 영수증·로컬 보관함·복구 절차로 연결 끊김·PC 종료·중복 실행에도 결과를 잃거나 두 번 반영하지 않는다 | H4 영수증(운영), 강제 종료 시험, 복구 화면 | 대화창 실행은 세션이 끊기면 결과가 사라지거나 다시 시켜야 한다 |
| 실측 근거로 모델 선택 | 내 작업의 실제 실행 기록으로 작업 종류별 모델을 고르고 고정·되돌린다. 문맥 전달량·재조회·사용량을 실행마다 계측한다 | CR-003 모델 정책, CR-004 실행 경로 평가, H2 문맥 계측 | 서비스가 고른 기본 모델을 쓰게 되고, 내 작업 기준의 비교 근거가 남지 않는다 |
| 휴대폰에서 PC 실행기를 원격 조작 | 휴대폰에서 작업을 만들고 지시하면 PC의 Codex가 PC 원본으로 실행하고, 결과는 양쪽에서 같은 기록으로 본다 | 데스크톱 연결기, 상태 동기화(H9-3), 실물 휴대폰 점검(H9-5) | 휴대폰 앱은 PC의 로컬 파일·로컬 실행기와 연결되지 않는다 |

## 2. 같거나 오히려 불리한 점
- 대화 사용감: 실시간 스트리밍이 없고 응답이 느리다.
- 파일 형식: HWP·엑셀·이미지·HDF5 등을 아직 읽지 못한다(CR-009로 진행 예정).
- 회사 고유 기능: 웹 검색, 메모리, 캔버스, 음성, 앱 연결 등은 INNO를 거치면 쓰기 어렵다.
- 차별점이 화면에서 드러나지 않음: 교차 검증은 '위임'의 한 단계로 숨어 있고, 계측·근거는 상세 패널 깊숙이 있다.
- 단일 사용자: 공동 작업·권한 관리가 없다.

## 3. 강화 후보

| 후보 | 내용 | 차별점과의 관계 | 크기 | 의존 |
|---|---|---|---|---|
| ① 한 번에 교차 검증 | 결과마다 '다른 회사 모델로 검증' 버튼. 검증자는 원 결과·근거·수용 기준을 받아 통과·실패·확인 불가를 근거와 함께 남기고, 불일치를 한눈에 보여 준다 | 가장 큰 차별점(교차 검증)을 직접 체감하게 함 | 중 | H7 검토 경로 재사용 |
| ② 근거 추적 | 결론의 각 주장을 원본의 위치(파일·페이지·구간)와 연결하고, 근거 없는 주장을 표시한다 | 연구 신뢰성. 원본 비보관과 결합(위치만 저장) | 중~대 | 원본 범위 지정, 첨부 형식(CR-009) |
| ③ 모델 비교 화면 | 작업 종류별로 어느 모델이 통과율·재작업·사용량에서 나았는지 내 기록으로 보여 준다 | 실측 모델 선택을 눈에 보이게 | 중 | CR-004 근거 누적 |
| ④ 프로젝트 지식 | 프로젝트 공통 지침에 더해 결정 기록·용어집을 프로젝트 단위로 누적해 모든 실행에 전달 | 소유한 연구 맥락의 축적 | 중 | CR-008 프로젝트 |
| ⑤ 실행 중 진행 표시 | 실행 단계·중간 산출물을 짧은 간격으로 표시 | 불리한 점(사용감) 완화 | 중 | 연결기·Routine 보고 |

## 4. 권장 순서
1. CR-008 프로젝트 출시(진행 중) → CR-009 첨부 형식(사용자 요청: HWP·HWPX·XLSX·개방형 문서·RTF·코드·HDF5·이미지 등 보편 확장자).
2. ① 한 번에 교차 검증: 가장 큰 차별점을 가장 작은 비용으로 드러낸다.
3. ② 근거 추적: 연구 용도에서 신뢰를 만드는 핵심. CR-009 이후가 효과적이다.
4. ③ 모델 비교 화면, ④ 프로젝트 지식, ⑤ 진행 표시는 사용 기록이 쌓인 뒤 우선순위를 다시 정한다.

## 5. 결정이 필요한 것
- 강화 후보 중 무엇을 언제 할지(위 권장 순서의 승인 또는 변경).
- ① 교차 검증의 기본값: 결과마다 자동으로 할지, 사용자가 누를 때만 할지(구독 사용량이 늘어난다).
- ② 근거 추적의 범위: 결론 문장 단위로 할지, 핵심 주장만 할지.

## 6. 결정과 진행 (2026-10-07)
- 사용자 결정: 권장 순서를 승인했다("승인이 필요한건 승인할게"). ① 교차 검증은 **사용자가 누를 때만** 한다(자동 검증 없음, 구독 사용량 절약).
- ① 구현(운영 반영 전, 설계 docs/superpowers/plans/2026-10-07-cross-check.md): 완료된 원본 없는 최상위 결과에 "○○로 교차 검증" 버튼. 마지막 결과를 낸 모델과 다른 회사의 배정 가능 실행기(Codex ↔ Claude)로 새 검증 작업을 만들어 실행하고, 원래 작업에 "교차 검증 · 검증자 · 판정" 줄, 검증 작업에 "검증 대상" 줄을 보인다. 원본을 읽은 작업·병렬 작업·검증 작업은 대상이 아니다. 검증자는 원 결과를 신뢰하지 않는 데이터로 받아 "판정: 통과 | 부분 통과 | 실패 | 확인 불가"와 항목별 근거를 남긴다. 자동 재작업은 없다.
- ① 운영 반영: 2026-10-07~08 커밋 9da5347(Worker·Pages·연결기 재실행).
- ② 구현(운영 반영 전, 설계 docs/superpowers/plans/2026-10-08-source-evidence.md): 범위는 **핵심 주장 단위**(최대 30개). 원본 텍스트를 받은 데스크톱 최상위 실행(Codex·Claude Code)이 주장마다 원본 번호·위치·짧은 원문 인용(200자 이내)을 내고, 이 PC의 실행기가 인용이 받은 원문에 그대로 있는지(공백·대소문자 무시) 확인한다. 작업 상세의 "근거 추적" 구역에 "원문 확인 / 원문에서 찾지 못함 / 근거 없음"을 주장별로 보인다. 원본·전문은 올리지 않고 위치·짧은 인용·확인 결과만 남긴다(기록 전체 32KB 이내). 위치 표기와 주장의 옳고 그름은 확인하지 않는다. 클라우드 Routine 실행·하위·검토 실행·이미지만 있는 자료·로컬 전용 서버 모드는 대상이 아니다.
