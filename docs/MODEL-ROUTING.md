# 모델 배정과 검증

마스터가 요청을 이해하고 납품물·실패 비용·검증 기준을 정한 뒤 필요한 하위 작업의 모델을 선택합니다. 단순 요청과 직접 검토 요청은 위임하지 않습니다. 위임할 때만 작은 문맥을 전달하며 최대 동시 2개·역할 6개, 검증 실패 시 해당 작업의 상향 시도는 한 번입니다. 복잡한 해석과 최종 통합은 마스터가 맡습니다. 이 판단은 모델에 전달하는 실행 정책이며 모든 판단을 코드가 강제하거나 품질 동등성을 보장하지는 않습니다.

## Codex

설치된 CLI의 model/list로 실제 모델/effort 목록을 조회하고 메모리에 한 시간 캐시합니다. 조회 실패 시 하위 에이전트 기능을 끄고 마스터가 직접 처리합니다. 모델명과 effort를 명시해서 네이티브 하위 에이전트를 호출하도록 지시하고 동시 실행 제한은 CLI 설정에도 적용합니다. 마스터 모델은 현재 런타임 기본값을 유지합니다.

결과물의 inno-model-routing.json에서 선택 이유·검증 기준·검토 결과를 확인합니다. 이 파일은 실행기의 자기보고이며 runtimeVerified=false입니다. catalogMatch는 모델과 effort가 조회 목록에 있다는 뜻이지 실제 실행 모델을 독립적으로 확인했다는 뜻이 아닙니다. 보고서가 없으면 not_reported입니다. 파일 10개/용량 한도에 가까운 결과는 본문 결과를 우선 보존하고 보조 보고서는 생략할 수 있습니다.

## Claude

클라우드 Worker와 로컬 Routine 호출에 동일한 배정 계약을 포함합니다. 저장소의 .claude/agents에는 Haiku(명확한 추출), Sonnet(범위가 정해진 구현·분석), Opus(어려운 독립 검토) 정의가 있습니다. 이들은 후보이며 모든 작업에 전부 투입하지 않습니다. 모델별 하위 실행의 maxTurns를 제한하고 재귀 Agent 호출을 금지합니다. Routine의 기존 마스터 모델은 바꾸지 않습니다.

Claude 마스터는 위임 전에 INNO checkpoint_task에 배정 계획을 기록하고, 완료 시 inno-model-routing.json을 별도 결과로 등록하도록 지시받습니다. 요청한 별칭과 런타임이 확인한 모델을 구분하며 확인되지 않은 실제 모델은 null입니다. 계정·정책에 따라 모델이 치환되거나 사용 불가능할 수 있으므로 경고를 확인하고 마스터 직접 처리로 돌아갑니다. 자기보고를 독립된 실행 감사로 표시하지 않습니다.

Routine은 저장소 기본 브랜치를 새로 가져와야 새 에이전트 정의를 사용합니다. 프로젝트 정의를 못 읽어도 새 fire payload 정책은 전달되며, 명시적 모델 선택을 지원하지 않는 환경에서는 직접 처리합니다. 기존 Routine 환경·인증을 다시 등록할 필요는 없습니다.

## 현재 범위

2026-09-28 개발 브랜치 기준입니다. 운영 배포 완료 여부는 [진행 기록](PROGRESS.md)을 확인하세요. 아래 변경이 배포된 것으로 간주하지 않습니다.

클라우드 연결 작업은 Codex와 Claude 하위 작업을 각 1개씩 배정하고, 결과가 모이면 마스터 검토로 합치는 오케스트레이터를 갖췄습니다. 이것은 임의 개수의 에이전트를 구성하는 최종 목표 전체의 완료가 아닙니다. [제공자 간 순차 인계](PROVIDER-HANDOFF.md)도 별도 흐름으로 유지합니다.

연결된 데스크톱의 관리 실행에서는 Codex 네이티브 multi_agent를 끄고 INNO가 제공자별 하위 작업을 관리합니다. 앞 절의 네이티브 하위 에이전트 지시는 해당 기능을 사용하는 별도 실행 모드의 계약이며, 모든 실행에서 적용된다는 뜻이 아닙니다.

새 하위 배정이 성공하면 초기 기준 정책도 자동 생성됩니다. 현재 UI의 ‘다음 배정 모델 정책 보기’에서 저장된 정책·후보·고정 상태와 다음 배정 사유를 확인할 수 있습니다. 후보 등록은 AI 평가나 품질 검증을 시작하지 않습니다. 현재 구독 실행의 정상 관측만으로 자동 승격은 작동하지 않습니다. 실제 버전 미확인·동일 조건 비교 부족·운영 가용성 증거 수집 미연결이 남아 있으며 [평가 근거 수정안](MODEL-ROUTE-EVIDENCE-PROPOSAL.md)은 사용자 결정 대기입니다.

사용량은 실행기가 보고한 값과 실행 단계별 기록을 표시합니다. 미보고는 0이 아니며, 제공되지 않는 양쪽 구독 전체 잔여량을 추정해 자동 전환하지 않습니다. 토큰 절감률과 모든 작업의 동등 품질은 확인된 수치가 아닙니다. API 키나 유료 초과 사용을 켜지 않습니다.

## 사용 순서와 상태 해석

1. 일반 요청을 생성하고 필요한 원본을 현재 기기에서 연결합니다. 원본 연결은 별도 영구 업로드를 의미하지 않습니다.
2. 데스크톱 Codex 또는 Claude Routine으로 실행합니다. 로컬 Codex 실행에는 켜져 있고 연결된 데스크톱이 필요합니다.
3. 하위 작업이 만들어지면 해당 작업의 ‘다음 배정 모델 정책 보기’를 엽니다. 현재 작업의 저장된 배정과 앞으로 적용할 정책을 구분합니다.
4. 후보 등록·현재 정책 고정·고정 해제를 사용할 수 있습니다. 고정 해제만으로 AI 비교나 승격이 시작되지 않습니다. 예전 미등록 작업에는 수동 기준 정책 초기화가 표시될 수 있습니다.
5. ‘실제 버전 미확인’은 지정 모델명과 내부 제공 버전을 동일시하지 않는 표시입니다. Claude의 역할 별칭 변경을 Routine 실제 모델 변경이나 절감으로 해석하지 않습니다.
6. ‘초기 정책 저장 한도’는 일반 작업 실행 실패가 아닙니다. 해당 배정은 지원 모델 검증을 거쳐 진행하지만 새 정책 등록은 보류됩니다. 기존 정책이나 원본을 임의 삭제하지 않습니다.

모델 정책의 중대 회귀 철회 처리와 정상 리뷰의 중대 오류 판정 연결은 구분해야 합니다. 현재 정상 리뷰는 실패·확인 불가 기준을 기록하지만 중대 회귀 신호를 자동 생성하지 않습니다. 또한 추가 비교 예산 예약과 로컬 기한 처리는 내부 기반이며, 공개 비교 실행·전체 프로세스 종료 확인·예산 정산은 아직 연결 중입니다.

공식 근거: [Codex subagents](https://developers.openai.com/codex/subagents), [Claude subagents](https://code.claude.com/docs/en/sub-agents), [Claude Routines](https://code.claude.com/docs/en/routines). 지원 기능은 계정과 설치 버전에 따라 달라집니다.

## 관측 저장 실패 복구

개발 브랜치의 완료 부모 작업에서 `정책 관측 기록`을 확인할 수 있습니다. 저장소 오류 등으로 자동 재시도가 끝난 항목은, 이 기능을 지원하는 서버에 연결했을 때 **관측 기록 다시 수집**으로 다시 대기시킬 수 있습니다. 저장된 검토 결과만 다시 읽으며 AI 작업과 결과물은 다시 생성하지 않습니다. 기존 정기 처리(설정상 5분 주기)가 수집하므로 즉시 저장 완료로 바뀌지는 않습니다.

요청 후에는 서버 상태를 확인합니다. 확인에 실패하면 **상태 다시 확인**으로 조회만 수행합니다. 확인되지 않은 요청을 자동으로 반복하지 않습니다. 다른 기기에서 기록이 바뀌면 최신 상태를 읽고, 실패가 여전히 남아 있을 때 사용자가 다시 요청할 수 있습니다.

이 동작은 `실패`로 끝난 수집만 대상으로 합니다. 정책 미등록이나 검토 근거를 배정에 연결할 수 없는 상태는 먼저 해당 원인을 해결해야 합니다. 원인이 계속되면 기존 자동 재시도 한도 뒤에 다시 멈춥니다. 기록 저장 성공은 모델 품질 검증이나 자동 승격 완료를 뜻하지 않습니다. 운영 적용 여부는 PROGRESS.md를 확인하세요.
