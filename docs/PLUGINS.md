# 플러그인(Agent Skills) 등록부, 작업 적용, 효과 근거와 추천 (CR-007 S3·S4)

작성일: 2026-10-03. 근거: docs/PROVIDER-PLUGIN-PROPOSAL.md PLG-01~03·06, 설계·작업 기록 docs/superpowers/plans/2026-10-03-plugin-registry.md.

## 1. 범위와 원칙
- 1차 범위: 공식 카탈로그의 **스크립트 없는** Agent Skill(SKILL.md와 .md/.txt 참고 파일)만. MCP 서버·스크립트 포함 스킬은 아직 등록할 수 없다.
- 허용 출처: `github.com/anthropics/skills`의 `skills/<이름>`, `github.com/openai/skills`의 `skills/.curated/<이름>`. 40자리 커밋 SHA로 고정하며, 그 커밋이 카탈로그 기본 브랜치에 있어야 한다(포크에만 있는 커밋 거부).
- 자동 설치 없음. 가져오기·승인·사용 중지·삭제는 사용자가 화면(실행 영역의 "플러그인" 버튼)에서 직접 한다. 삭제는 확인 체크가 필요하다.
- 권한은 고정: 스크립트·네트워크·파일 접근 없음. 원본 자료와 비밀값에는 닿지 않는다. 유료 API나 추가 AI 평가를 쓰지 않는다.
- 효과 근거·삭제 검토·추천(PLG-04·05)은 6·7절(S4). 정상 작업 관측만 쓰고 추가 AI 비교는 하지 않으며(예산 0), 효과가 좋다고 주장하지 않는다.

## 2. 가져오기와 검토
1. 카탈로그·스킬 이름·커밋을 입력하면 Worker가 커밋 위치 확인 → 폴더 목록 검사(최상위 파일만, 최대 8개·48KB) → 직접 만든 주소로 내려받아 목록의 크기·git blob SHA-1·UTF-8과 일치하는지 확인한다. 어긋나면 아무것도 저장하지 않는다.
2. 파일별 SHA-256과 전체 내용 해시를 기록하고 정적 검토를 한다.
   - 경고: 셸·네트워크 명령, 외부 링크, 비밀값·환경 파일 언급, 지시 우회 문구, 프롬프트 경계 문구, AI 탐지 언급.
   - 차단(승인 불가, PLG-06): AI 작성 탐지기를 겨냥한 회피, AI 작성 사실 은폐, 사람이 쓴 것으로 위장하려는 지시. "탐지를 회피하지 말 것" 같은 부정문은 경고로만 남는다.
3. 카드에서 상태·커밋·해시·검토 결과와 "고정된 원문 보기"(그 커밋의 GitHub 폴더)를 확인한 뒤 **검토한 내용으로 승인**한다. 승인 요청은 화면에 보인 내용 해시를 함께 보내며, 서버는 저장된 텍스트를 다시 해시해 다르면 승인 대신 사용 중지한다.
4. 같은 내용을 다시 가져오면 상태가 유지되고 손상된 저장 사본은 복구된다. 다른 내용이면 검토 대기로 돌아간다.

## 3. 작업 적용
- 사용자 선택: 작업 화면의 플러그인 대화상자에서 승인된 플러그인을 최대 3개, 적용 이유와 함께 고른다(실행 중이 아닐 때).
- 마스터 배정: 루트 작업의 마스터는 승인된 플러그인 목록(id·설명)을 보고, 위임하는 자식에게 이유와 함께 배정할 수 있다. 미승인 배정은 거부된다.
- 실행 시점 재확인: 승인 상태와 저장 텍스트 해시를 다시 확인한 것만 전달한다(실행당 합계 64KB). 승인 해제·내용 불일치·삭제·크기 초과는 제외하고 이유를 남긴다.
- 전달 방식: 프롬프트에 해시에 묶인 태그로 감싼 "사용자 승인 플러그인" 구역을 넣는다. 플러그인은 작업 지시·안전 규칙·실행 소유권·콜백·전달 규칙을 바꿀 수 없고, 플러그인 속 명령 실행이나 링크 열기는 금지된다고 명시한다.
- 기록: 실행마다 `pluginDelivery = {applied, skipped}`를 저장하고 재개 지점 카드에 한 줄로 보인다. applied는 "프롬프트에 넣어 보냄"을 뜻한다(Claude Routine이 인증 등으로 거절한 경우에도 보낸 사실은 기록). 데스크톱 결과의 보고는 작업의 선택과 저장된 플러그인 버전(id·해시)이 맞을 때만 저장한다. 이전 데스크톱은 플러그인을 넣지 않으므로 기록이 남지 않는다.

## 4. 저장
`metadata` 테이블의 `plugin:<id>`(레코드)와 `plugin_content:<id>`(텍스트) 키. 스키마 변경 없음, 등록 최대 32개. 레코드 변경은 비교 후 교체로 동시 변경을 막는다. S4에서 `plugin_archive`(삭제한 플러그인의 근거, 최근 50개), `plugin_discovery:<카탈로그>`(추천 후보), `plugin_discovery_lock`(하루 1회 갱신 잠금)이 추가됐다.

## 5. 알려진 한계
- 32개 상한 확인과 쓰기가 원자적이지 않아 동시 가져오기 시 몇 개 넘을 수 있다.
- 승인된 스킬도 결국 지시문이므로 프롬프트 주입 위험을 완전히 없애지는 못한다(경계·우선순위 문구, 정적 검토, 크기 상한, 사용자 승인으로 줄인다).
- 정적 검토 규칙은 휴리스틱이다. 새로운 회피 표현은 놓칠 수 있고, 규칙 버전(rulesVersion)으로 기록된다.
- PLG-04 중 하지 않은 것(부분 완료):
  - 효과 근거는 완료·미완료 수와 시간·토큰 중앙값뿐이다. 독립 품질 검토 결과와 비AI 회귀 검사는 아직 근거에 넣지 않는다. 시간·토큰은 보여 주기만 하고 판정에 쓰지 않는다.
  - "명확히 우수한 대체가 검증되면 새 작업에서 자동 제외"와 "회귀 시 이전 조합으로 복구"는 구현하지 않았다. 추가 비교 예산이 0이라 우수함을 검증할 근거가 생기지 않기 때문이다. 대신 나빠 보이면 사용자에게 제외·삭제 검토를 권하고, 사용자가 작업 선택에서 빼거나 삭제한다.
- 비교는 일치한 작업 종류·실행기 묶음을 합쳐서 본다(묶음별 가중 비교는 아님). 같은 작업 안의 재시도도 각각 한 번의 실행으로 센다(작업 5개 이상 조건으로 한 작업에 쏠린 근거를 막는다).
- PLG-05 후보에는 작업과의 관련성 판단이 없다(AI 평가를 쓰지 않음). 위험 표시는 SKILL.md의 정적 검사뿐이고, 나머지 파일은 가져올 때 검사한다.
- 이미 등록한 스킬은 목록에서 빠지므로, 카탈로그에 새 판이 나와도 "새 판 있음"을 알리지 않는다(등록 레코드에 git blob 해시가 없어 비교하지 못함). 다시 가져오기로 확인한다.
- 카탈로그 파일 목록이 2MB를 넘거나 잘리면 그 카탈로그는 "확인되지 않음"으로 남는다(하위 경로 대체 조회 없음). 인증 없는 GitHub 조회라 공유 IP의 요청 한도에 걸리면 같은 방식으로 늦춰 다시 시도한다.

## 6. 효과 근거와 삭제 검토 (PLG-04, S4)
- 기록: 실행이 끝나거나 실패할 때 실행 이력(usageHistory)에 그 실행이 받은 플러그인(id·내용 해시, 최대 3개), 실행 당시 작업 종류(없으면 general, 64자), 실패 종류(실패일 때)를 남긴다. 서버가 기록한 행만 믿고, 가져오기·복원한 이력의 값은 버린다.
- 비교: 최근 90일 동안 **지금 등록된 내용(같은 내용 해시)**의 플러그인을 받은 실행과, 플러그인 없이 같은 작업 종류·같은 실행기(Claude/Codex 등)에서 끝난 실행을 비교한다.
- 세는 실행: 완료, 그리고 실행 자체가 멈춘 실패(출력 상한·알 수 없는 중단)만. 한도·인증·연결·재시작·실행기 사용 불가처럼 시작 전이거나 연결 문제로 끝난 실행은 빼고, 플러그인 쪽에서 뺀 횟수를 함께 보인다. Claude Routine이 한도·인증으로 거절한 실행도 플러그인은 "보냄"으로 기록되지만 여기서 빠진다. 실행기 프로그램을 시작하지 못한 경우(ENOENT·EACCES)와 검토 입력을 읽지 못해 시작하지 않은 검토는 "실행기 사용 불가"로 분류된다.
- 이번 변경 전의 기록(작업 종류가 함께 남지 않은 행)은 양쪽 모두에서 세지 않는다. 그런 행은 실패 종류도 없어서, 세면 완료만 남고 실패가 빠져 비교 쪽이 실제보다 좋아 보이기 때문이다.
- 판정(`public/core/plugin-evidence.mjs`):
  - 승인한 지 30일이 지났는데 90일 동안 한 번도 보내지 않았으면 "사용되지 않음 — 필요 없으면 삭제를 검토".
  - 어느 쪽이든 5회 미만이거나 서로 다른 작업 5개 미만이면 "근거 부족 — 효과를 판단하지 않음"(MOD-06과 같은 최소 표본 원칙).
  - 적용한 실행의 미완료 비율이 비교 실행보다 30%p 이상 높고, 단측 Fisher 정확 검정 p ≤ 0.05일 때만 "새 작업에서 빼거나 삭제를 검토". 예: 5회 중 3회 대 5회 중 1회는 차이가 40%p여도 p≈0.26이라 판정하지 않는다.
  - 그 밖에는 "뚜렷한 차이가 확인되지 않음"이다. 좋아졌다고 말하지 않는다.
- 화면: 카드마다 적용·비교 횟수, 완료·미완료, 시간·토큰 중앙값(적용/비교), 제외 횟수와 판정 문장을 한 줄로 보인다.
- 자동 제외·자동 삭제는 없다. 삭제는 기존처럼 확인 체크 후 사용자가 한다. 삭제할 때 그 시점의 근거를 `plugin_archive`에 함께 남기며, 화면의 "삭제한 플러그인의 근거"에서 볼 수 있다. 보관 기록은 방금 읽은 값 위에만, 검토한 내용 해시가 아직 등록돼 있을 때만 쓰고, 그 쓰기가 된 경우에만 레코드와 텍스트를 지운다(한 묶음). 동시에 두 개를 지워도 두 근거가 모두 남고, 그 사이 다시 가져온 새 내용은 지우지 않는다(409).
- 조회: `GET /api/plugin-evidence` → `{plugins:[근거], archive:[삭제 기록]}`. 아무것도 바꾸지 않는다.

## 7. 카탈로그 후보 (PLG-05, S4)
- 허용 카탈로그 두 곳(1절)을 Worker 예약 실행이 읽는다. 한 번의 예약 실행은 **때가 된 카탈로그 하나만** 읽어 요청 수를 작게 유지한다(기본 브랜치 커밋 1회, 파일 목록 1회, SKILL.md 최대 8개). 각 카탈로그의 목록은 **하루 1회**만 다시 읽는다.
- 아직 읽지 못한 SKILL.md가 남으면(실행 시간 상한으로 중간에 끊긴 것 포함) 한 시간 뒤 같은 목록에서 다음 8개를 읽는다. 내용(blob 해시)이 그대로인 SKILL.md는 다음 날 다시 읽지 않고, 읽기에 실패한 것만 다음 날 다시 시도한다.
- 시간 상한: 요청마다 8초, 한 번의 실행 전체 60초. 갱신 잠금은 120초 임대이고, 만료 시각이 없는 잘못된 잠금 행도 막지 않는다. 실패하면 마지막 목록을 유지하고 15분부터 늘어나는 간격(최대 하루)으로 다시 시도한다.
- 읽는 것: 기본 브랜치 커밋, 그 커밋의 파일 목록(2MB 상한, 잘린 목록은 쓰지 않음), 가져올 수 있는 스킬의 SKILL.md(각 48KB 상한, 카탈로그당 스킬 200개까지).
- 가져올 수 있는 기준은 등록부와 같다. SKILL.md가 있고 그 이름(name)이 폴더 이름과 같아야 하며, 최상위의 공백 없는 이름의 .md/.txt만, 8개·48KB 이하여야 한다. 안 되는 후보는 이유와 함께 접힌 목록에 보인다. 이미 등록한 스킬은 빠진다.
- 후보 카드: 설명, 근거("공식 카탈로그 ○○의 기본 브랜치(커밋)에 있음" + 확인한 만큼의 판정 + "작업과의 관련성은 판단하지 않음"), 위험(SKILL.md 정적 검사 경고, 차단 규칙 해당, "SKILL.md만 미리 검사함")을 보인다. SKILL.md를 아직 읽지 않았거나 읽지 못했으면 "가져올 수 있음"이라고 하지 않고 그 사실과 "가져올 때 모든 파일을 검사함"을 보인다(가져오기 자체는 2절의 검사를 그대로 거친다).
- 자동 설치는 없다. "가져오기 (검토 후 승인)"을 누르면 목록의 커밋으로 고정해 2절의 가져오기·검토를 그대로 거치며, 승인은 따로 한다. 차단 규칙에 해당하는 후보에는 가져오기 버튼이 없다.
- 조회: `GET /api/plugin-recommendations` → `{sources:[카탈로그 상태], candidates:[후보]}`.
